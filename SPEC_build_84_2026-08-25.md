## Lane C · Testers get full Pro

Allowlist, grant function, signup trigger, backfill, one-statement revoke. All server-side — lands
before the build and works the moment a tester installs.

### Four constraints this must respect

1. **`source` must be `'manual'`.** The CHECK permits `manual, app_store, play, promo, grandfather, mac_app_store, stripe, amazon, rc_billing`. `'tester'` is not legal, and adding it would mean touching the constraint, `packages/engine-contracts/src/billing.ts`, the vendored `_shared/engine-contracts/billing.ts` and a re-bundle — for nothing. `PROVIDER_SOURCES` already excludes `manual` from every revoke path, so a manual grant is structurally unrevokable by the store layer. Distinguish testers by `note`.
2. **Idempotency is `WHERE NOT EXISTS`, never `ON CONFLICT`.** There is deliberately no unique index on `(user_id, entitlement_key)` — grants are an append-only succession — so `ON CONFLICT DO NOTHING` has no arbiter and inserts a duplicate every run.
3. **Keys come from `v_tier_entitlements`, not a literal list.** It resolves to **five** today. Assert five; do not assume six.
4. **The signup trigger must never fail a signup.** It sits on `auth.users`; an uncaught exception aborts registration for every user. Swallow and log — a missing comp is recovered by re-running the backfill; a broken signup is not.

### Shape

```sql
-- 1 · allowlist: service-role only, no client privilege, RLS with zero policies
create table public.tester_allowlist (
  email text primary key check (email = lower(btrim(email))),
  note text, added_by text, added_at timestamptz not null default now()
);
alter table public.tester_allowlist enable row level security;
alter table public.tester_allowlist force  row level security;
revoke all on public.tester_allowlist from anon, authenticated;
grant  all on public.tester_allowlist to service_role;

-- 2 · grant: every key the pro tier resolves to, idempotent, bounded
create function public.grant_tester_pro(p_user_id uuid, ...) returns integer
  security definer set search_path = public as $$
    -- assert v_tier_entitlements('pro') returns 5 keys, else raise
    insert into public.user_entitlements (user_id, entitlement_key, source, expires_at, note)
    select p_user_id, v.entitlement_key, 'manual', now() + interval '90 days', 'tester_allowlist'
      from public.v_tier_entitlements v
     where v.tier_key = 'pro'
       and not exists ( ... active grant with > 14 days left ... );  -- no-op AND renewal
  $$;

-- 3 · auto-grant on signup, exception-swallowing
create trigger on_auth_user_created_tester_grant after insert on auth.users ...

-- 4 · backfill / renew (safe to re-run on a schedule)
select public.grant_tester_pro(u.id) from auth.users u
  join public.tester_allowlist a on a.email = lower(btrim(u.email));

-- 5 · the undo
update public.user_entitlements set revoked_at = now()
 where revoked_at is null and source = 'manual' and note = 'tester_allowlist';
```

### The ownership rule that will silently break this

`public.user_entitlements` (and the new `tester_allowlist`) carry **FORCE ROW LEVEL SECURITY**, which
applies to the table owner too. Both functions work only because the migration role carries
`BYPASSRLS` and therefore owns them. **Do not re-own them** — the allowlist lookup would return no rows
and every tester would be silently un-comped. Same trap already documented on
`enforce_free_card_slot_limit` (`bill_001_p3:143-149`), which is the only reason it was checked here.

### What granting actually turns on

All three launch flags are already **true** in production, so a grant is immediately visible — no flag
flips needed for receipt scanning, statement analysis or the widget. Two live consequences:

- `ambient_widget` being on puts a **locked tile** on the lock screen of any non-entitled user who has added the widget.
- The paywall is on for all 80 accounts and cannot sell. Recommendation: **turn it off** and comp the testers, so the only people seeing Pro are people who can use it. One `UPDATE` either way.

## B7 — CONFIRMED AND FIXED

Owner's Paywall screenshot, iPhone 16 Pro Max (1320x2868 px = 440x956 pt @3x, top inset 62pt):

```
sheet's own top edge ...............  62 pt from the screen top
top of the X chip ..................  78 pt below that edge
the chip itself ....................  96 x 96 px = 32 x 32 pt   <- exactly SHEET_X_CHIP_SIZE
16 (spacing[4]) + 62 (window inset)   78 pt                     <- exact
```

`SheetXChip` renders at `top: theme.spacing[4] + topOffset`; `ScreenDismissButton` passed
`topOffset={insets.top}`. Inside an iOS `modal` the card is already below the status bar, so a second
one was added — to the chip AND to each screen's `paddingTop`, independently (absolute `top` measures
from the border box here, not the padding box, which is why 78 and not 140).

**Fix:** `src/navigation/sheetTopInset.ts` (new) exports `useSheetTopInset()` =
`Platform.OS === "ios" ? 0 : insets.top`. Read by the four sheet screens for `paddingTop` and by
`ScreenDismissButton` for the chip. **Default is the sheet**, so a new sheet screen that forgets is
CORRECT rather than broken. `TransactionRecordingScreen` opts out with `<ScreenDismissButton fullScreen />`
— it is `fullScreenModal` and genuinely has a status bar to clear (commit 38362c7's fix, preserved).

Route-awareness via `useRoute()` was tried first and rejected: it throws outside a screen, two suites
render these screens in a bare container, and 21 tests went red. A platform check needs no context.

1. **`jest.setup.ts:188-192` mocks `useSafeAreaInsets` to `{ top: 0 }`.** Zero is the one value that

   this bug. `src/navigation/__tests__/sheetTopInset.test.tsx` overrides it with a real 62pt inset.
   **Detector proven twice**: reverting `useSheetTopInset` to `insets.top` makes it fail with
   `Received: 78` where 16 is expected — the same number the screenshot measured. Belongs in
   `HANDOFF_pro_lane_2026-08-23.md` §4.5 ("the jest harness lies in specific ways").

2. **`verify:sheet-layout` has been CRASHING, on HEAD, not just on this branch.** It dynamically

# B1 and B2 — DONE

## B1 — the widget stops acting on a guess

**Root-caused in the context, not patched at the widget.** The chain was:
`runtime_flags` read fails -> `EntitlementsContext` clears the flag map -> an empty map reads as every
flag off -> `useFeatureGate` reports `feature_disabled` -> `useWidgetSnapshot` treats that as an
instruction to DELETE the payload -> and the provider re-reads on every AppState `active`. One
foreground with the radio down erased a working tile, one-way, until the next successful
recommend-here-v2 — which needs the user to open the Now screen. Hours, or never.

The defect was that a FAILED read and a DELIBERATELY DARK flag were indistinguishable.

**Fix, in three layers:**

1. `contexts/EntitlementsContext.tsx` gains `resolved: boolean` — "the last read actually produced an
   answer", as distinct from `loading` ("a read is in flight"). One flag covering both reads, because
   every gate needs both answers; the independence that matters — a flag failure must not discard known
   entitlements — is preserved. `false` outside the provider; **`true` for a signed-out user**, because
   "no session" is a definite answer, not a missing one.
2. `hooks/useFeatureGate.ts` gains `resolved` on the result and a FOURTH reason, **`"unknown"`**. Checked
   only on the closed branch: an open gate is already evidence the reads returned, except in `restrict`
   mode where a failed flag read correctly leaves the feature free (the documented fail-open direction,
   asserted by a new test).
3. `widget/useWidgetSnapshot.ts` guards BOTH destructive paths on it — `publish` and the lapse effect.
   Without the second guard a failed read presents as a lapse: entitled tile overwritten with locked, or
   removed outright if the flag half is what failed.

Only three places branch on the gate `reason`, so the fourth value was cheap. `StatementImportScreen:164`
maps `unknown` in with `feature_disabled` deliberately — both are dead ends with nothing to sell, nothing
irreversible happens there, and the conservative copy is right.

## B2 — the payload no longer outlives the session

`useWidgetSnapshot` has exported a `clear()` for this since WIDGET-001 and **nothing ever called it**.
The hook lives on NowScreen; signing out swaps the whole signed-in tree for AuthStack in the same commit,
so the screen unmounts before any effect of its can run. The last entitled snapshot — merchant, card,
issuer, earn rate — stayed in the App Group indefinitely, on the lock screen, readable by whoever picked
the phone up next. Same after account deletion.

Fixed in `contexts/AuthContext.tsx`, which outlives that tree: `clearWidgetPayload()` is called from
**both** `signOut` (covering the `isAuthSessionMissingError` early return too) and `clearSession` (the
deleted-account and expired-session path). Fire-and-forget and swallowing, on the widget lane's standing
rule that a widget must never block, delay or fail anything — least of all the way out of the app.

## What the five actually fix

1. **Every receipt capture on Android 7–9 failed.** On API ≤ 28 `expo-image-picker`'s
   `launchCameraAsync` asks for `WRITE_EXTERNAL_STORAGE` alongside `CAMERA` and requires both granted
   (`ImagePickerModule.kt` — `WRITE_EXTERNAL_STORAGE.takeIf { SDK_INT < Q }`). A permission absent
   from the manifest is auto-denied, and `app.config.ts` blocked it — so the capture rejected with
   `ERR_USER_REJECTED_PERMISSIONS` immediately after the user granted the camera, and the screen
   showed the generic "couldn't read this receipt". minSdk is 24. **This is `withCameraManifest`,
   and it is exactly the case the `blockedPermissions` comment had reserved.**

2. **The French widget picker was English.** `@expo/config-plugins` chains same-type mods
   **last-registered-first**, so listing `withCardCoachWidgetStrings` *after* the library made it run
   *before* it: the receiver did not exist yet, the label stayed an English literal, and the
   library's `translatable="false"` overwrote ours — which also makes the `values-fr` override an
   `Untranslatable` lint finding. **An audit of this tree on 2026-08-25 read the array position and
   called the ordering correct. It was wrong.** Array position cannot express this; the plugin now
   defers through `withAfterEarlierMods` and is position-independent.

3. **Registration was half the widget fix.** `storage.ts` called `requestWidgetUpdate({ widgetName })`
   with no `renderWidget`. The library does not wake the headless task there — it resolves every
   placed instance and calls `renderWidget` for each in the app's own JS. With no renderer that is a
   TypeError inside its per-widget callback, an unhandled rejection, on **every snapshot write**, and
   never a redraw. So even with the handler registered the tile would update only on the 30-minute
   tick, never when the app learned something.

4. **The paywall would have read "not on sale" forever once a key existed.** `PurchasesContext`
   fetched offerings before the user resolved, got `UninitializedPurchasesError`, swallowed it to
   `[]`, and never refetched — for the life of the process, on both platforms. Invisible today only
   because no `CARDCOACH_REVENUECAT_*` key is set anywhere.

5. **The Top pick pill was painted over by its own card.** Android orders siblings by ELEVATION and
   ignores `zIndex` when they disagree; the card carries `elevation: 12` from `getGoldGlowShadow`,
   so it ate exactly the overlap the pill's negative margin creates. Shipped clipped since 1.0.3.

6. **Card chooser tail and capture shutter** sat under the Android navigation bar.
